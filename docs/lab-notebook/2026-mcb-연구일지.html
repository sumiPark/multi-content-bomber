1. 목표 및 배경

SNS 마케팅에서 동일한 콘텐츠라도 플랫폼마다 문법이 다르다. YouTube는 검색 SEO와 시청 완료율, Instagram은 체류시간(Engaged Time)과 저장, TikTok은 1초 안에 시청 여부가 결정되는 훅(hook)이 핵심 신호다. 사람이 이 세 톤을 각각 작성하면 시간이 많이 들고 품질 편차가 크다. 본 연구는 한 번의 API 호출로 선택된 플랫폼 전체의 캡션을 동시 생성하여, 핵심 메시지는 유지하되 플랫폼별 톤·길이·해시태그 전략만 달라지도록 설계하는 것을 목표로 한다.

2. 기술 개요 - 카피라이팅 8원칙의 프롬프트 주입

캡션은 정보 전달이 아니라 사용자의 다음 행동(스크롤 멈춤 → 시청 → 저장/댓글)을 설계하는 도구로 정의한다. 인지심리학·행동경제학 근거를 가진 8개 원칙을 시스템 프롬프트에 명시적으로 주입한다.

  • Curiosity Gap - 결과·숫자는 노출하되 방법은 숨긴다. (Loewenstein, 1994)
  • Specificity Bias - "큰 절약" 대신 "287만원 절약"처럼 구체적 숫자로 신뢰·기억률 상승.
  • Loss Aversion - 손실 강조가 이득 강조보다 행동 유도력이 약 2배. (Kahneman & Tversky, 1979)
  • Pattern Interruption - 예측을 깨는 표현으로 자동 주의 유발. TikTok 훅의 최우선 원칙.
  • Open Loop / Zeigarnik - 미완성 정보가 시청 지속률에 직접 기여.
  • First-Line Hook - Instagram "더보기" 유도로 체류시간 확대.
  • Question-Driven CTA - 질문형 마무리가 평서형 대비 댓글률 1.5~2배.
  • Save-Worthy Framing - 저장은 좋아요보다 알고리즘 가중치가 높음.

4. 구현 과정

단일 출처 설계서 docs/caption-engine.md를 기준으로 lib/ai/caption-generator.ts·lib/ai/prompts.ts를 구현했다. GPT-4o 호출 파라미터와 출력 스키마는 다음과 같다.

// 선택된 플랫폼만 required로 동적 구성
{
  youtube?:   { title, description, hashtags[], category }
  instagram?: { caption, hashtags[], cover_text }
  tiktok?:    { caption, hashtags[] }
}
// 호출: temperature 0.7(재생성 0.85), response_format: json_schema(strict)
  • 플랫폼별 글자수 후처리 안전망 - AI가 한도를 어겨도 코드에서 단어 경계 트리밍, # 누락 태그 자동 prepend, TikTok은 caption 본문에서 정규식으로 해시태그를 추출해 메타데이터와 동기화.
  • 프리셋 오버라이드 - 제품 리뷰형·튜토리얼형·이벤트 홍보형 등 톤 지침을 [캡션 스타일 가이드] 블록으로 system/platform 프롬프트 위에 우선 삽입.
  • 재생성 - 이전 응답을 assistant 메시지로 넣고 "다른 hook 전략으로" 요청, 같은 콘텐츠의 ai_captions 컬럼을 UPDATE(신규 row 미생성 → dangling row 방지).

5. 문제 해결 및 최적화

  • 클릭베이트 처벌 회피 - CTR만 높고 시청 완료율이 낮으면 알고리즘이 오히려 처벌한다. 시스템 프롬프트에 거짓 약속·과장 표현 금지를 명시하고, Loss Aversion은 실제 한정성·시즌성일 때만 허용하도록 제약.
  • N회 호출 → 1회 호출 - 초기엔 플랫폼별 개별 호출을 검토했으나, 메시지 일관성 저하와 비용 증가로 기각. 선택 플랫폼을 하나의 스키마 required로 묶어 단일 호출로 통합.
  • zod 이중 검증 - strict JSON Schema 통과 후에도 zod로 재검증하여 런타임 타입 안전성 확보.

6. 결과 및 평가

선택 플랫폼 3종의 캡션을 단일 호출로 일관되게 생성하는 엔진을 완성했다. 플랫폼별 톤·해시태그 전략이 명확히 분기되면서도 핵심 메시지가 유지되어, 수동 작성 대비 작성 시간을 대폭 단축했다. 8원칙의 명시적 주입으로 "번역체·광고문구체" 산출물이 크게 줄었고, 후처리 안전망 덕분에 글자수 초과로 인한 게시 실패를 원천 차단했다. 향후 플랫폼 개별 재생성, 성과 데이터 기반 원칙 가중치 튜닝을 과제로 남긴다.

1. 발생 문제

SNS 업로드는 느리고(Instagram 컨테이너 폴링, 대용량 영상 멀티파트) 실패가 잦다(토큰 만료·rate limit·미디어 규격). 한 채널의 실패가 다른 채널을 막으면 안 되고, 같은 job이 중복 게시되어도 안 된다. 초기에는 BullMQ + Upstash Redis + Railway 상주 워커로 구성했으나, 상주 워커가 Redis를 24/7 폴링하여 Upstash 무료 50만 커맨드/월을 며칠 만에 소진(실제 한도 초과로 발행 전체가 마비)했고, 상주 프로세스 관리 부담(좀비 워커 누적)과 이중 인프라 의존이 드러났다.

이 파이프라인은 단순 API 호출의 나열이 아니라, ① 여러 워커가 동시에 실행돼도 같은 발행 건을 중복 처리하지 않을 것, ② 처리 도중 프로세스가 크래시해도 유실 없이 복구할 것, ③ 상주 프로세스·외부 큐 없이도 위 두 보장을 유지할 것이라는 상충하는 요구를 동시에 만족해야 했다. 정해진 정답이 없어 여러 실행 모델을 시제작·비교하는 과정이 필요했고, 이 기술적 불확실성의 해소가 본 연구의 핵심이다.

2. 기술 개요 - 발행 상태 머신

발행 1건을 publish_jobs 테이블의 한 행으로 두고, 명시적 상태 전이로 관리한다. 모든 전이는 status_history(jsonb)에 timestamp·message로 append하여 감사 로그로 남긴다.

채널별 독립 상태 - 한 계정 실패가 다른 계정 발행을 막지 않음
  • 멱등성 - jobId = publish_jobs.id(UUID)로 중복 발행을 차단. 외부 게시는 성공했는데 DB 기록만 실패하면 재게시(중복) 대신 경고 로그 후 정합성 sweep에 위임.
  • 부분 실패 격리 - 한 채널 실패 시 해당 건만 RETRYING으로 남고 나머지는 정상 진행. attempts < 3 동안 재시도.
  • 토큰 자동 갱신 통합 - 발행 직전 만료 임박 토큰은 즉시 refresh 후 재암호화 저장. 토큰이 폐기된(invalid_grant) 계정은 is_active=false로 마킹해 헛된 재시도를 차단.

3. 시스템 아키텍처 - Postgres 큐 + GitHub Actions

큐를 별도 인프라 없이 publish_jobs 테이블 자체로 대체한다. 핵심은 claim_due_publish_jobs RPC다.

핵심 RPC - FOR UPDATE SKIP LOCKED로 due job(예약 시각 지난 PENDING/RETRYING + stale PROCESSING 회수)을 원자적으로 선점. 여러 워커가 동시 실행해도 같은 job을 두 번 잡지 않는다.

실행 기반은 다음 대안을 시제작·검토한 끝에 결정했다. 단순히 저렴한 안을 고른 것이 아니라, 신뢰성 요구(중복 방지·긴 처리 시간·장애 복구)를 충족하는 안을 가려낸 것이다.

4. 구현 과정

  • worker/process-due.ts - 엔트리: claim → 처리 → 토큰 sweep → exit. 상주 loop 제거, BullMQ·ioredis 의존성 삭제.
  • 기존 발행 상태 머신(publish-processor.ts)은 그대로 재사용 - 큐 모델만 교체하고 처리 로직은 보존.
  • 재시도는 BullMQ backoff 대신, 실패 시 row를 RETRYING으로 남기면 다음 sweep이 다시 claim. 워커가 처리 중 크래시해도 claim RPC가 stale PROCESSING을 회수하여 유실 방지.
  • 동시성은 워커 스크립트가 CONCURRENCY로 제어, rate limit은 플랫폼 어댑터에서 처리.

6. 결과 및 평가

본 연구의 핵심 성과는 별도 큐 인프라 없이도 동시성·멱등성·장애 복구를 보장하는 발행 구조를 도출·검증한 것이다. 발행 1건을 명시적 상태 머신으로 관리해 부분 실패 격리·감사 로그를 확보했고, FOR UPDATE SKIP LOCKED 기반 원자적 선점으로 여러 워커 동시 실행 시에도 중복 처리·유실이 없음을 확인했다. 여러 실행 모델을 비교·시제작한 끝에 도달한 이 구조는, 부수적으로 상주 프로세스·외부 큐를 제거해 상시 운영비까지 0으로 낮췄다. 즉시 발행은 dispatch로 지연이 없고, 예약 발행만 cron best-effort로 5~30분 지연을 감수하되, 신뢰성이 더 필요하면 process-due.ts를 그대로 재사용해 유료 스케줄러로 승격할 수 있다. 실제 겪은 한도 초과·발행 마비를 임시방편이 아니라 구조 재설계로 근본 해결한 점에서 연구적 의의가 있다.

발행 대상 현황 - YouTube·Instagram은 실계정 발행을 검증했고, TikTok은 발행 어댑터(Direct Post / PULL_FROM_URL)까지 구현했으나 TikTok 앱 심사 승인 전이라 현재는 샌드박스(테스트) 계정 발행만 가능하다. 승인 시 코드 변경 없이 동일 어댑터로 프로덕션 발행에 편입되며, 이는 본 파이프라인이 어댑터 인터페이스로 플랫폼을 추상화한 설계의 이점이다. (캡션 자동 생성(연구 001)은 승인과 무관하게 3개 플랫폼 모두 동작한다.)
