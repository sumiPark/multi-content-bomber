먼저 · 30초 한 문장 요약

MCB는 영상·이미지 하나를 올리면, AI가 유튜브·인스타그램·틱톡용 문구를 각각 자동으로 만들어 주고, 정해둔 시간에 세 곳에 알아서 올려주는 서비스입니다.

연구 001 · AI 캡션 자동 생성 엔진

일련번호 001 · 2026.05.01~05.15

콘텐츠 하나로, 세 플랫폼 문구를 한 번에

같은 콘텐츠라도 유튜브·인스타·틱톡은 잘 먹히는 문구가 다릅니다. AI가 세 가지를 한 번에, 각 플랫폼 성격에 맞게 만들어 줍니다.

🟡 이렇게 비유하세요

같은 요리를 세 나라 손님 입맛에 맞게 통역해 주는 카피라이터입니다. 요리(핵심 메시지)는 똑같고, 말투와 양념(플랫폼별 톤·해시태그)만 다르게 냅니다.

왜 필요했나

유튜브는 검색, 인스타는 체류·저장, 틱톡은 1초 안의 훅(hook)이 핵심입니다. 사람이 세 번 따로 쓰면 느리고 품질 편차가 큽니다.

꼭 기억할 용어 3개
GPT-4o Vision 이미지를 보고 이해하는 AI JSON Schema strict 정해진 칸에만 답을 채우게 강제 카피 8원칙 심리학 기반 문구 규칙

Q"그냥 챗GPT에 물어본 거랑 뭐가 다른가요? 이게 왜 연구인가요?"

A

단순 호출이 아닙니다. ① 클릭·체류·저장을 유도하는 심리학 8원칙을 프롬프트에 주입했고, ② AI가 글자수·해시태그 규칙을 어겨도 코드가 자동 교정하는 후처리 안전망을 넣었고, ③ 한 번의 호출로 3종을 동시에 만들어 메시지 일관성과 비용을 동시에 잡도록 설계한 것이 연구의 핵심입니다.

Q"영상은 AI가 어떻게 이해하나요?"

A

AI는 영상을 직접 못 봅니다. 그래서 영상에서 대표 사진(프레임) 한 장을 뽑아 사진처럼 넣어 줍니다. 이때 서버가 아니라 사용자 브라우저에서 직접 추출해 서버 부담을 0으로 만든 것도 이 연구의 최적화 포인트입니다.

연구 002 · 자동 발행 파이프라인 & 저비용 인프라

일련번호 002 · 2026.05.18~06.23

여러 SNS에 안정적으로 자동 발행 (+ 운영비까지 절감)

콘텐츠를 여러 채널에 자동으로 올리는 '뒷단(백엔드)' 전체입니다. 핵심은 하나가 실패해도 안전하고 중복 없이 발행하는 신뢰성이고, 운영비 0은 그 구조를 잘 설계해서 따라온 결과입니다.

🟡 이렇게 비유하세요

여러 택배를 송장으로 각각 추적하듯, 각 발행을 상태로 관리합니다. 그리고 24시간 상주 경비원(월급+대기 비용)을 필요할 때만 부르는 알바로 바꾸듯, 별도 대기줄 서버 대신 이미 있는 데이터베이스를 대기표(큐)로 재활용해 운영비를 없앴습니다.

⚠️ 발표할 때 이 톤 주의 (세액공제 관점)

"공짜로 쉽게 했다"로 말하면 연구의 난이도가 낮아 보여 손해입니다. 대신 "여러 대안을 시제작·비교하며 신뢰성을 검증한 끝에, 운영비 없이도 동시성·복구를 보장하는 구조를 도출했다"로 말하세요. 세액공제는 연구원 인건비 기준이라 운영비 0이 공제를 줄이지 않습니다 — 다만 "쉬웠다"는 인상만 주지 않으면 됩니다.

이 연구는 세 가지를 한 번에 풉니다
  • 안정성택배 송장처럼 각 발행을 상태(접수→처리→성공/실패/재시도)로 추적. 하나 실패해도 나머지는 발송되고, 실패는 자동 재시도(3회), 같은 걸 두 번 올리는 중복도 없음.
  • 보안계정 접근 열쇠(토큰)를 금고(암호화)에 보관하고, 만료되기 전에 자동으로 새 열쇠로 교체.
  • 운영비상주 서버 없이 필요할 때만 실행(GitHub Actions)하도록 설계해, 상시 운영비를 0으로 (신뢰성 확보의 부수 성과).
왜 필요했나 (실제 사고)

처음엔 상주 서버를 24시간 켜뒀는데, 그 서버가 대기줄(Redis)을 쉬지 않고 확인하는 바람에 무료 사용량을 며칠 만에 소진 → 발행 전체가 마비됐습니다. 게다가 서버·대기줄 비용이 이중으로 들었습니다. 이 사고가 재설계의 출발점입니다.

꼭 기억할 용어 4개
publish_jobs 발행 한 건 = 한 줄(송장) 멱등성 두 번 실행돼도 결과는 한 번 SKIP LOCKED 같은 건 두 번 안 잡는 DB 기법 GitHub Actions / cron 예약·자동 실행

Q"이게 왜 연구인가요? 그냥 서버에 올리는 배포 아닌가요?"

A

단순 배포가 아니라 실제 장애를 겪고 구조를 재설계한 연구입니다. 여러 워커가 동시에 돌아도 중복이 없어야 하고(SKIP LOCKED), 처리 중 죽어도 복구돼야 하고, 상주 서버 없이 이를 유지해야 하는 상충하는 요구가 있었습니다. QStash·Railway Cron 등 대안을 시제작·비교한 끝에 데이터베이스를 대기줄로 재활용하는 구조를 도출해 중복·유실 없이 해결했고, 운영비 0은 그 결과로 따라온 것입니다. 문제 발견 → 대안 비교 → 재설계 → 검증이 모두 담긴 게 핵심입니다.

Q"한 채널이 실패하면 전부 취소되나요?"

A

아니요. 채널마다 독립입니다. 실패한 건만 재시도하고, 이미 성공한 건은 그대로 둡니다. 처리 도중 서버가 죽어도 '처리 중'에 멈춘 건을 다음 실행이 회수해 다시 처리하므로 유실도 중복도 없습니다.

Q"계정 토큰을 그냥 저장하면 안 되나요?"

A

유출되면 곧바로 계정 도용입니다. 그래서 앱 안에서 암호화해 저장하고, 관리자 권한으로만 열람하며, 일반 접근은 DB 보안 규칙(RLS)으로 막습니다. 만료 임박 토큰은 발행 직전·주기적으로 자동 갱신합니다.

Q"그럼 예약 발행 시간이 정확한가요?"

A

즉시 발행은 지연이 없습니다. 예약 발행만 30분 주기라 5~30분 오차가 생길 수 있는데, 그 대가로 운영비 0과 운영 단순화를 얻었습니다. 더 정밀해야 하면 유료 스케줄러로 승격만 하면 되고 코드는 그대로 재사용합니다.

Q"세 플랫폼 다 실제로 올라가나요? (틱톡 포함)"

A

정직하게 답하세요. 캡션 생성(001)은 유튜브·인스타·틱톡 3개 모두 동작합니다. 발행(002)은 유튜브·인스타는 실계정 발행을 검증했고, 틱톡은 발행 어댑터까지 구현했지만 틱톡 앱 심사 승인 전이라 현재는 테스트(샌드박스) 계정만 가능합니다. 다만 어댑터 구조로 만들어서 승인되면 코드 변경 없이 바로 프로덕션에 편입되도록 설계했다 — 이렇게 말하면 "외부 승인 대기"라는 한계가 오히려 좋은 설계 근거가 됩니다.

그대로 외워도 되는 발표 스크립트

30초 프로젝트가 뭐냐고 물으면

"MCB는 영상이나 이미지 하나를 올리면, AI가 유튜브·인스타그램·틱톡용 문구를 각각 자동으로 만들고, 정해둔 시간에 세 곳에 알아서 올려주는 서비스입니다. 저는 크게 두 가지, AI 캡션 생성 엔진과 안정적인 자동 발행 구조(운영비까지 절감)를 연구했습니다."

2분 연구 내용을 설명하라고 하면

"두 축입니다. 첫째, AI 캡션 엔진(001) - 플랫폼마다 잘 먹히는 문구가 달라서, 심리학 8원칙을 넣은 프롬프트로 세 플랫폼 문구를 한 번에 생성합니다. 영상은 AI가 직접 못 보니 브라우저에서 대표 프레임을 뽑아 서버 부담 없이 분석에 씁니다. 둘째, 자동 발행 파이프라인(002) - 여러 채널 발행을 택배 송장처럼 상태로 추적해 하나가 실패해도 안전하고 중복이 없게 했고, 계정 토큰은 암호화 저장·자동 갱신합니다. 특히 상주 서버가 무료 한도를 소진해 발행이 마비된 실제 사고를 겪고, 여러 대안을 시제작·비교한 끝에 데이터베이스를 대기줄로 재활용하는 구조를 도출해 중복·유실 없이(운영비까지 0으로) 해결했습니다. 두 연구 모두 실제 겪은 문제를 설계로 풀어낸 것이 핵심입니다."

비상용 "가장 자랑할 만한 성과는?"

"상주 서버가 대기줄을 계속 확인해 무료 한도를 소진하고 발행이 마비된 실제 사고를, 여러 대안을 검증한 끝에 동시성·복구를 보장하면서 운영비 없이 돌아가는 구조로 재설계해 해결한 것입니다. 문제 발견부터 대안 비교·재설계까지 직접 한 연구라 가장 기억에 남습니다."
